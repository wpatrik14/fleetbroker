# Why relay targets are addressed by tmux session name, not peer name

`ListAgents` surfaces two different kinds of things:

- **Local sessions on the same host**, shown with their tmux location (e.g.
  `some-name-4c [abcdef] · tmux claude:0.0`). The name prefix before the
  bracketed suffix is generated by the harness and **changes across
  restarts** - it is not a stable identifier.
- **Remote Control peers** on entirely different hosts/networks, shown by
  their `--name`/`--remote-control-session-name-prefix` identity (e.g.
  `OtherSiteFleetNode`), with no tmux location at all.

Because the local name suffix is not stable, a relay prompt that says "send
this to the session literally named `some-name-4c`" would silently stop
working the next time that host reboots and the harness picks a new suffix.

The fix used throughout this project: **address the local relay target by its
stable tmux session name** (`claude`, by convention - every fleet node's
installer creates its persistent session under this exact name) rather than
by the harness-generated peer name. The relay prompt's allow-list is "the one
peer whose *location* is tmux session `claude`," not "the peer named X."

This is also why the deny-list in the relay prompt (`forbidden_tmux_sessions`,
`forbidden_peer_names`) is a defense-in-depth belt-and-suspenders measure, not
the primary safety mechanism: the primary mechanism is the allow-list being
exactly one entry, addressed by something stable. If you find that a Remote
Control peer's name (a second real fleet member's name, for example)
is *also* unstable across its own restarts, treat the deny-by-name half of the
prompt as advisory only and rely on the tmux-location allow-list as the real
boundary.

## Practical convention for a new fleet

- Every node's persistent local session runs in a tmux session named exactly
  `claude` (see `provision/claude-tmux.service.tmpl`).
- Every node's Remote Control identity (`--name`) is a separate, human-chosen
  fleet name - this is what shows up when a *different* host's `ListAgents`
  looks at this node, and it's fine (expected, even) for this name to differ
  from the tmux session name.
- A relay config's `target_tmux_session` is always `"claude"` for relaying
  *within* a single host. Relaying *across* hosts is not something the relay
  module does directly - it's exactly the "let the persistent home session
  decide whether to forward this onward via SendMessage to a Remote Control
  peer" step described in the README.
